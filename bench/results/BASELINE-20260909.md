# Performance baseline — 2026-09-09

The first committed baseline. Everything before this was "run the scripts locally if you want
numbers", which meant there was nothing for a future regression to be measured against.

**Hardware:** Apple M1 Max / 10 cores / 64GB RAM / macOS 26.6.2
**Toolchain:** rustc 1.91.0 (the pinned toolchain, not the ambient one), release profile
**Fixture:** `tests/fixtures/sample_multi_tile.ome.zarr` (1024x1024, two levels)

Reproduce with `./scripts/load.sh` and `cargo bench -p ziv-tiling`. Numbers are only comparable
against a run on the same hardware — treat cross-machine comparisons as meaningless.

## HTTP throughput (`scripts/load.sh`, oha 1.16)

| Run | req/s | mean latency | p99 | requests |
|---|---|---|---|---|
| hot (30s, 50 conns) | 87,332 | 0.57 ms | 2.24 ms | 2,620,394 |
| cold[0] (7s, 10 conns) | 62,273 | 0.16 ms | 0.31 ms | 435,990 |
| cold[1] | 59,879 | 0.16 ms | 0.37 ms | 419,301 |
| cold[2] | 61,139 | 0.16 ms | 0.36 ms | 428,143 |
| cold[3] | 57,549 | 0.17 ms | 0.46 ms | 402,956 |

All responses 2xx.

**Read the "cold" rows carefully.** They are cold only for their *first* request: each URL is
then hammered for seven seconds, and every subsequent response is a tile-cache hit. So these
measure cache-hit serving of four distinct keys, not render cost. That is why their latency is
*lower* than the hot run's — fewer connections, not less work. For actual per-render cost, use
the criterion numbers below, which bypass HTTP entirely.

## Render cost (`cargo bench -p ziv-tiling`, criterion)

| Benchmark | Median |

Criterion's own `target/criterion` baselines are gitignored; these medians are the committed

machine and read criterion's own change report.
